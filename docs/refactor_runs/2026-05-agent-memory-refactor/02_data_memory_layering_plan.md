# 02 Data And Memory Layering Plan

Status: accepted direction, pending implementation design.

Baseline commit before this refactor: `7984fb1`.

## Goal

OKRA should move from a context/RAG-centered data flow to a layered financial
data and memory system.

The current pattern to avoid is:

```text
collect data -> pack a large context -> retrieve a few text chunks -> ask LLM
```

The target pattern is:

```text
raw observations -> canonical facts -> derived signals -> decision events
-> outcome events -> strategy memory -> strategy skills
```

Different data classes must have different lifecycle, storage, retrieval,
trust, and learning behavior. RAG is only one retrieval mechanism inside this
larger system. It is not the memory architecture itself.

## External Reference Bias

This plan adopts the user-approved direction based on the FinRobot, FinGPT, and
FinMem discussion.

Useful reference ideas:

- FinRobot: separate perception, brain, and action. OKRA should separate data
  acquisition, reasoning/memory, and executable decision artifacts.
- FinGPT: finance is highly dynamic, so data updates and data engineering must
  be first-class. OKRA should not rely on a monolithic model remembering stale
  facts.
- FinMem: profiling, layered memory, and decision-making are connected. Memory
  should convert layered financial information into better decisions, not just
  retrieve text.

## Core Principle

OKRA's long memory is not a RAG library.

It is a layered financial memory system:

- facts guarantee accuracy
- signals explain the present
- events record decisions
- outcomes provide feedback
- strategy memory stores reusable rules and patterns
- strategy skills store reusable procedures

Daily action tickets must consume these layers and feed their outcomes back into
the memory system.

## Data Layer 1: Raw Observations

Raw observations preserve source data with minimal rewriting.

Examples:

- fund quotes
- official NAV
- estimated NAV
- intraday proxies
- news and announcements
- screenshots and OCR/VLM parse results
- actual trades
- position snapshots
- realtime PnL snapshots
- API responses and source health

Required properties:

- source
- source URL or source file
- fetched_at
- observed_at or as_of_date
- provider status
- raw payload or normalized copy
- parse confidence if applicable
- stale / fallback status

Usage:

- audit
- reprocessing
- source quality analysis
- rebuilding canonical facts or signals

Raw observations should not be directly used as final decision truth unless no
canonical fact exists and the missing-data state is explicit.

## Data Layer 2: Canonical Facts

Canonical facts are OKRA's source of truth. They should be structured and
protected from free-form LLM rewriting.

Examples:

- current portfolio state
- fund code and fund name
- fund type and category
- holding units
- current value
- cost basis
- official NAV
- official NAV date
- real daily PnL after official NAV confirmation
- benchmark and proxy mapping
- fund tradability
- minimum transaction amount
- settlement or confirmation rules
- actual execution state

Required properties:

- entity type
- entity key
- fact type
- value
- source
- as_of_date
- valid_from
- valid_until if applicable
- confidence
- authoritative flag
- last_updated_at

Rules:

- LLMs may propose fact corrections, but should not directly overwrite
  canonical facts.
- Conflicting facts must be represented as conflicts, not silently merged.
- Canonical facts should be queryable through structured lookup, not vector
  search first.

## Data Layer 3: Derived Signals

Derived signals interpret canonical facts and raw observations.

Examples:

- market regime
- theme rotation
- fund relative strength
- estimate versus official NAV gap
- proxy freshness
- data reliability score
- crowding risk
- event risk
- allocation drift
- action readiness

Required properties:

- signal id
- signal type
- entity scope
- value or direction
- strength
- confidence
- freshness
- evidence refs
- generated_by
- generated_at
- valid_until

Rules:

- Signals can be generated by deterministic code, statistical models, LLM
  agents, or hybrid logic.
- Signals are not facts. They can expire, conflict, and be contradicted.
- Signals should feed debate and action-ticket generation.

## Data Layer 4: Decision Events

Decision events record how the system reasoned and what it proposed.

Examples:

- analyst evidence bundle
- bull case
- bear case
- trader synthesis
- action ticket
- risk adjustment
- final approval or block
- user override

Required properties:

- event id
- date
- entity scope
- related action ticket id
- actor or agent
- input refs
- output refs
- decision reason
- confidence
- uncertainty
- created_at

Usage:

- traceability
- replay
- learning
- agent quality scoring
- future similar-case retrieval

Decision events are the bridge between today's analysis and tomorrow's memory.

## Data Layer 5: Outcome Events

Outcome events record what happened after a decision.

Examples:

- T+1 result
- T+5 result
- T+20 result
- official NAV confirmation
- execution confirmation
- missed opportunity
- avoided loss
- premature de-risk
- over-conservative hold
- data-quality failure

Required properties:

- outcome id
- related action ticket id
- horizon
- evaluation date
- return or PnL measurement
- benchmark or proxy comparison
- classification
- supporting evidence
- diagnosis
- generated_at

Usage:

- validate strategy memory
- strengthen or weaken adaptive policies
- score agent roles
- identify useful bear warnings
- detect soft constraints that wrongly blocked opportunity

## Data Layer 6: Strategy Memory

Strategy memory stores reusable investment learning.

Examples:

- "QDII estimate strength without official NAV confirmation should reduce add
  size."
- "When high-volatility themes rebound from deep loss, use conditional add
  rather than immediate large add."
- "If bear warning about stale proxy was correct twice recently, lower same
  signal confidence."
- "A hold decision without a review trigger often misses actionable moves."

Memory types:

- `adaptive_policy`
- `market_pattern`
- `fund_pattern`
- `risk_pattern`
- `execution_pattern`
- `anti_pattern`
- `agent_quality_memory`

Required properties:

- memory id
- memory type
- scope
- rule or pattern text
- status
- confidence
- support count
- contradiction count
- last supported at
- last contradicted at
- evidence refs
- effect on action tickets

Status lifecycle:

```text
observation -> candidate_policy -> active_soft_policy
-> strengthened | weakened | archived
```

Strategy memory should not be treated as immutable truth. It is learned,
evaluated, and revised.

## Data Layer 7: Strategy Skills

Strategy skills store reusable procedures rather than single rules.

Examples:

- QDII daily judgment procedure
- high-volatility theme add-before-close procedure
- fund conversion review procedure
- official PnL reconciliation procedure
- weak-signal watch-to-action procedure

Required properties:

- skill id
- name
- scope
- trigger conditions
- steps
- required data
- expected output
- failure modes
- related policies
- version
- success metrics

Usage:

- the strategy/trader agent can call a skill during action-ticket generation
- memory can propose new skills or revisions
- user can review or promote important skills

## Retrieval Model

Retrieval must depend on data type.

### Structured Lookup

Use for canonical facts and execution-critical data.

Examples:

- current holdings
- official NAV
- real daily PnL
- available cash
- tradability
- settlement state

This should be deterministic and auditable.

### Similar-Case Retrieval

Use for episodes, outcomes, anti-patterns, and historical market cases.

This can use vector search, keyword search, time filters, and metadata filters.

### Policy / Skill Registry Retrieval

Use for active strategies, soft constraints, and reusable procedures.

This should prioritize:

- scope match
- current status
- confidence
- recency
- support versus contradiction
- user confirmation if available

## Retrieval Pack For Action Tickets

Every action ticket should consume a layered retrieval pack.

Target shape:

```json
{
  "facts": {},
  "signals": {},
  "similar_episodes": [],
  "active_policies": [],
  "anti_patterns": [],
  "skills_used": [],
  "missing_data": []
}
```

The strategy/trader agent should know:

- what the current facts are
- what today's signals say
- what similar historical cases did
- which active policies apply
- which anti-patterns warn against the action
- which skills were used
- which missing data reduces confidence

## Adaptive Soft Constraints

The user explicitly accepted that soft constraints should be self-forming and
long-memory-backed.

Soft constraints are not static config walls. They are adaptive policies.

Example:

```json
{
  "policy_id": "soft:qdii_delay_reduce_size",
  "type": "soft_constraint",
  "scope": "fund_group:qdii",
  "rule": "QDII estimated NAV high but official NAV not confirmed, reduce add size by one bucket",
  "status": "active_soft_policy",
  "support_count": 4,
  "contradiction_count": 1,
  "confidence": 0.72,
  "effect": {
    "adjust_size_bucket": -1,
    "require_trigger": "official_nav_confirmed"
  }
}
```

Soft constraints can:

- reduce size
- reduce confidence
- add a trigger
- convert executable action to conditional action
- increase watch priority
- require later review

Soft constraints should not:

- directly veto an action
- silently force hold
- override canonical facts
- become hard constraints without a separate design decision

## Hard Constraints

Hard constraints are preserved for now.

Their exact boundary will be discussed separately.

Current examples:

- identity and holding safety
- cash and sellable amount safety
- minimum transaction size
- future-data prevention
- critical missing data
- explicit non-tradable state
- execution or settlement impossibility

## Memory Growth Loop

The memory system should grow from action outcomes.

Loop:

```text
action ticket -> risk adjustment -> final action -> execution result
-> horizon outcome -> diagnosis -> memory update -> future retrieval pack
```

The system should learn:

- which action patterns work
- which bear warnings are valuable
- which risk adjustments saved losses
- which soft constraints wrongly killed opportunity
- which agent is too conservative or too aggressive
- which triggers improve timing
- which data sources are unreliable

## Relationship To RAG

RAG remains useful, but it is not the top-level design.

Use RAG for:

- similar historical episodes
- long text evidence
- policy explanation
- anti-pattern retrieval
- skill documentation retrieval

Do not use RAG as the first tool for:

- current holdings
- official NAV
- real daily PnL
- cash
- tradability
- settlement status
- exact action ticket state

Those require structured storage and deterministic lookup.

## Candidate Storage Domains

Names are provisional.

- `db/raw_observations/`
- `db/canonical_facts/`
- `db/derived_signals/`
- `db/decision_events/`
- `db/action_tickets/`
- `db/outcome_events/`
- `db/strategy_memory/`
- `db/strategy_skills/`

Implementation should reuse existing data where practical, including portfolio
state, execution sync, long memory, validated advice, decision ledger, RAG
indexes, and daily workspace artifacts. The new design should not require
throwing away current durable user state.

## Implementation Notes

Likely migration sequence:

1. Define schemas for facts, signals, decision events, outcomes, adaptive
   policies, and skills.
2. Build adapters from current portfolio, execution, NAV, quote, news, and long
   memory artifacts into layered records.
3. Produce retrieval packs for shadow action tickets.
4. Link action ticket outcomes to memory updates.
5. Promote adaptive soft constraints from repeated outcomes.
6. Add strategy skills after repeated policies become procedural.
